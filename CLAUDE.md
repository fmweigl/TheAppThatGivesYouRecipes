# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Kotlin Multiplatform + Compose Multiplatform app targeting Android, iOS (arm64 + simulator arm64), and Desktop (JVM). Early stage: a bottom navigation bar (Navigation 3) with two tabs: the `recipe` feature, whose tab shows random meals from TheMealDB, and the `about` feature, which lists the app's open source libraries and their licenses.

Open source under the Apache License 2.0 (`LICENSE`), copyright "The YetAnotherMealsApp contributors". `ATTRIBUTIONS.md` credits TheMealDB as the source of recipe data and images and holds the dietary disclaimer; keep it current when data sources change.

The README's badges are shields.io images: Kotlin and Compose Multiplatform read their versions from `gradle/libs.versions.toml` on GitHub, the others are static. Update the static ones when their facts change (the API badge with `android-minSdk`, platforms, license, "tracking: none" with the privacy policy).

`PRIVACY.md` is the app's privacy policy and describes only what the app does today: no data collection, requests to TheMealDB, and Coil's on-device image cache. When a change affects data handling (on-device storage such as favorites or settings, opening external links, new network services, analytics or crash reporting), update the policy and its "Last updated" date in the same change. The app shows the file itself (About → Privacy), so keep it to headings and plain paragraphs.

## Commands

- Android debug build: `./gradlew :androidApp:assembleDebug`
- Desktop run: `./gradlew :desktopApp:run` (hot reload: `./gradlew :desktopApp:hotRun --auto`)
- iOS: open `iosApp/` in Xcode and run from there (the Xcode build phase runs `:composeApp:embedAndSignAppleFrameworkForXcode`, which produces the static `Shared` framework)
- Tests:
  - JVM tests per module: `./gradlew :feature:recipe:domain:jvmTest` (also `:feature:recipe:data`, `:feature:recipe:ui`, `:core:domain`, `:core:data`, `:core:network`, `:core:designsystem`)
  - iOS simulator tests: `./gradlew :feature:recipe:domain:iosSimulatorArm64Test`
  - Single test: `./gradlew :feature:recipe:domain:jvmTest --tests "io.github.fmweigl.yetanothermealsapp.recipe.domain.SomeTest.someMethod"`
  - Tests exist in `:core:domain` (`Result`), `:core:data` (`safeApiCall` error mapping), `:core:network` (client config and Koin module), `:feature:recipe:data` (repositories + mapping, via Ktor `MockEngine` and an in-memory Room database; `safeDbCall`), `:feature:recipe:ui` (ViewModel; screen-reader semantics of `RandomRecipeScreen` in `jvmTest`, with Compose `ui-test` on the desktop runtime), `:feature:about:ui` (`toTextBlocks`) and `:core:designsystem` (color contrast).

Static analysis: detekt (`./gradlew detekt`, also part of `check`). The `meals.detekt` convention plugin applies it to every module with the shared config `config/detekt/detekt.yml` on top of detekt's defaults, and analyzes all source sets under `src/`. Fix findings rather than suppressing them; suppress only with an inline comment explaining why (see `SafeApiCall.kt`). Functions annotated `@Composable` are exempt from `FunctionNaming`. No formatter (ktlint, spotless) is configured.

## CI

GitHub Actions (`.github/workflows/ci.yml`) runs `./gradlew detekt jvmTest :androidApp:assembleDebug` on pushes and pull requests to `master`. Run this command locally and make sure it passes before a task counts as done. CI doesn't build or test iOS.

The second job, `release`, runs on every push to `master` after `build` passes. It restores the upload keystore from the secret `RELEASE_KEYSTORE_BASE64` into `$RUNNER_TEMP`, builds `:androidApp:assembleRelease :androidApp:bundleRelease -PappVersionCode=<run number>` with the signing settings and TheMealDB key from secrets (as environment variables, read by `configProperty`), and creates the GitHub Release `v1.0.<run number>` (with `gh release create --generate-notes`) with the signed APK attached as `yetanothermealsapp-1.0.<run number>.apk`. When the repository variable `PLAY_PUBLISHING` is `true`, it also uploads the bundle and R8 mapping to Google Play's production track with `r0adkll/upload-google-play`. `versionCode` comes from the Gradle property `appVersionCode` (default 1), `versionName` is `1.0.<versionCode>`, so both go up with every master build. Every master build that passes CI is released, so keep `master` releasable. The required secrets are listed in the job's comment in `ci.yml`.

## Build logic

Shared Gradle setup lives in convention plugins in the included build `build-logic/` (wired in through `includeBuild("build-logic")` in `pluginManagement`). It reads the root version catalog. **Every new KMP module must apply exactly one of these plugins**; its own build file then only holds the plugin, the `namespace` and `packageOfResClass` (UI modules) and module-specific dependencies.

| Plugin | Use for | Provides |
|---|---|---|
| `meals.kmp.domain` | `domain` modules | KMP with the shared targets; kotlin-test in commonTest; `verifyDomainDependencies` (runs as part of `check`) |
| `meals.kmp.data` | `data` modules (also `:core:network`) | KMP with the shared targets + kotlinx-serialization; kotlin-test, kotlinx-coroutines-test, ktor-client-mock in commonTest |
| `meals.kmp.room` | `data` modules with a Room database (`:feature:recipe:data`) | everything from `meals.kmp.data` (which it applies) + `com.android.kotlin.multiplatform.library` with an `android` target (Room on Android needs a `Context` and Android-specific generated code) + KSP + Room 3 (`androidx.room3`, schemas exported to the module's `schemas/`, committed); room3-runtime and sqlite-bundled in commonMain; room3-compiler on every target's KSP configuration (`kspAndroid`, `kspJvm`, `kspIosArm64`, `kspIosSimulatorArm64`) |
| `meals.detekt` | every module (applied by the KMP plugins; `:composeApp`, `:androidApp`, `:desktopApp` apply it directly) | detekt with the shared config, covering all source sets |
| `meals.kmp.compose` | Compose library modules that aren't features (`:core:designsystem`) | KMP + `com.android.kotlin.multiplatform.library` + Compose MP + Compose compiler; shared targets plus `android` (compileSdk/minSdk from the catalog, JVM target 11); Android resources enabled + compose components-resources (for Compose resources); Compose runtime/foundation/material3/ui in commonMain; kotlin-test in commonTest |
| `meals.kmp.feature.ui` | feature `ui` modules | everything from `meals.kmp.compose` (which it applies) + kotlinx-serialization (for `NavKey`s); `:core:designsystem`, lifecycle viewmodel-compose + runtime-compose, koin-compose-viewmodel, navigation3-runtime in commonMain; kotlinx-coroutines-test in commonTest |

- The target list (jvm, iosArm64, iosSimulatorArm64) exists once, in `sharedKmpTargets()` (`build-logic/convention/.../KmpTargets.kt`). It sets JVM target 11 on `jvm()`: Android uses the `jvm` variant of modules without an `android` target, and an Android compilation (JVM 11) can't inline functions compiled for a newer JVM. The Android library defaults are in `androidLibraryDefaults()`. `:composeApp` calls both directly; the root `build.gradle.kts` loads the convention plugins with `apply false` so these helpers are importable from module build scripts.
- **Domain rule:** a domain module's commonMain must not depend on Ktor (`io.ktor`), Koin (`io.insert-koin`), AndroidX (`androidx`, `org.jetbrains.androidx`) or Compose (`org.jetbrains.compose`), directly or through another module. `verifyDomainDependencies` fails `check` and names the offending dependency.
- `build-logic` gets the Gradle plugins as `compileOnly` dependencies derived from the catalog's `[plugins]` entries; add new plugins there the same way.
- `theMealDbApiKeySource()` (`TheMealDbApiKey.kt`), called from `:core:network`'s build file, registers `generateTheMealDbApiKey`, which writes `internal const val THE_MEAL_DB_API_KEY` into a generated commonMain source directory (`build/generated/theMealDbApiKey/`). The key comes from the first of: Gradle property `theMealDbApiKey`, `theMealDbApiKey` in the root `local.properties`, the `THE_MEAL_DB_API_KEY` environment variable; otherwise TheMealDB's public test key `1`, so debug builds without the supporter key (contributors, CI) still work. Keys are restricted to `[A-Za-z0-9_-]`, and the task is kept out of the build cache.
- `configProperty(name, environmentVariable)` (`ConfigProperty.kt`) is the lookup for every secret build setting: Gradle property, then the root `local.properties`, then the environment variable. Both the TheMealDB key and the signing settings use it.
- Android release signing: `releaseSigning(project)` (`ReleaseSigning.kt`), called in `:androidApp`'s `android {}` block, signs `release` with the Play upload key from the `configProperty`s `releaseStoreFile` (relative to the repository root, or absolute), `releaseStorePassword`, `releaseKeyAlias` and `releaseKeyPassword` (`RELEASE_STORE_FILE`, ...). Without all four, `checkReleaseSigning` (a dependency of `preReleaseBuild`) fails release builds; it only records which settings are missing, never their values. Keystores are gitignored (`*.jks`, `*.keystore`). Never commit, print or log the passwords or the keystore.
- Android release builds use R8 (`isMinifyEnabled`, `isShrinkResources`). The libraries ship their own consumer rules, so `androidApp/proguard-rules.pro` only keeps line numbers. After changing dependencies, serialization or navigation keys, build a signed release and run through the app (including restoring after process death, which serializes the `NavKey`s), since R8 problems only show at runtime.
- Release builds refuse the test key. The key is compiled once, in `:core:network`, for every variant, so the check is a separate task: `theMealDbApiKeySource()` also registers `:core:network:checkTheMealDbProductionKey` (fails if the key is `1`), and `requireTheMealDbProductionKey { taskName -> ... }` makes matching tasks depend on it: `preReleaseBuild` in `:androidApp`, every `*Release*` task in `:desktopApp` (`runRelease`, `packageRelease*`), and `linkRelease*` (iOS release frameworks, i.e. Xcode's Release configuration) in `:composeApp`. A new app module or release path needs the same hook.

## Architecture

- `:composeApp` is the UI entry point for all platforms and holds the main navigation. It owns the root composable `App()` (`io.github.fmweigl.yetanothermealsapp`), depends on the feature `ui` and `data` modules, defines `initKoin()` (`di/Koin.kt`) listing each feature's Koin modules, and produces the static iOS `Shared` framework. Each platform entry point calls `initKoin()` once at startup, then hosts `App()`:
  - `androidApp/`: `MealsApplication.onCreate()` calls `initKoin { androidContext(...); modules(debugModules(...)) }` (empty in release, the optional screenshot mode in debug); `MainActivity` calls `setContent { App() }`. A plain `com.android.application` module (not KMP) that depends on `:composeApp`.
  - `desktopApp/`: `main()` calls `initKoin()`, then opens a Compose `Window` with `App()`. A `kotlin("jvm")` module (not KMP) using `compose.desktop`, depends on `:composeApp`.
  - `iosApp/`: `iOSApp.init()` calls `KoinKt.doInitKoin(config: nil)` (Kotlin `initKoin` is exported with a `do` prefix); SwiftUI wraps `MainViewController()` from `composeApp/src/iosMain`, imported in Swift as `import Shared`
- Navigation uses Navigation 3 (JetBrains multiplatform `navigation3-ui` and `lifecycle-viewmodel-navigation3`; the runtime is Google's multiplatform `androidx.navigation3:navigation3-runtime`, pinned to the version `navigation3-ui` requires). It lives in `:composeApp`'s `navigation` package, following the multiple back stacks recipe:
  - `AppNavigation` holds the `Scaffold` with the bottom `NavigationBar` and the `NavDisplay`. The `NavDisplay` consumes the `Scaffold`'s insets, so a screen with its own `TopAppBar` doesn't pad for the status bar again. `topLevelDestinations` lists the tabs (the first is the start route); the `entryProvider` calls each feature's entry registration (`randomRecipeEntry()`).
  - `NavigationState` keeps the selected tab and one `NavBackStack` per tab, saved across configuration changes and process death. Each stack has its own saveable-state and ViewModel-store decorators, so ViewModels are scoped to their entry and a tab keeps its state while another is shown. `Navigator` changes it: `navigate()` switches tabs or pushes onto the current stack, `goBack()` pops, and from the root of another tab returns to the start tab ("exit through home").
  - Every `NavKey` must be `@Serializable` and registered in `navKeyConfiguration` (`AppNavigation.kt`): outside Android, back stacks can only be saved with explicitly registered subtypes.
- `:composeApp` and `:feature:recipe:ui` use the newer AGP `com.android.kotlin.multiplatform.library` plugin: Android config lives inside `kotlin { android { ... } }`, not a top-level `android {}` block. In UI modules that block only sets `namespace`; the rest comes from `meals.kmp.feature.ui`.
- `feature/recipe/` is a feature folder with three modules, referenced through type-safe project accessors (`projects.feature.recipe.domain`):
  - `:feature:recipe:domain`: models and repository interfaces. KMP (jvm + iOS), with no Android or Compose dependencies.
  - `:feature:recipe:data`: repository implementations, depends on `domain`. Its only public declaration is the Koin module `recipeDataModule`; everything else is `internal`. Same constraints as `domain`, but it applies `meals.kmp.room`, so it also has an `android` target, which Android uses instead of `jvm`. Gets its `HttpClient` from `:core:network` and decodes responses with kotlinx.serialization. Meals are decoded as raw `JsonObject`s and mapped in `MealMapper.kt` because of the numbered `strIngredientN`/`strMeasureN` fields. `RecipeRepository` loads a random recipe (`random.php`) or one by id (`lookup.php?i=`); when there are no meals TheMealDB answers HTTP 200 with `"meals": null` or a message such as `"Invalid ID"`, which `MealsResponse.meals` turns into an empty list and `getRecipe` into `DataError.NotFound`. It also holds the app's Room database, `RecipeDatabase` (`database` package, file `recipes.db`): the table `favorite_recipe` stores each favorite completely (tags and ingredients as JSON via `RecipeColumnTypeConverters`), so `FavoritesRepository` (`observeFavorites`, `observeIsFavorite`, `addFavorite`, `removeFavorite`) works offline, and `getRecipe(id)` reads a saved recipe from the database before asking TheMealDB. Where the file lives is platform-specific (`platformDatabaseModule`, `expect`/`actual`: Android's database directory, the OS's app data directory on desktop (`~/.local/share/YetAnotherMealsApp`, `%APPDATA%`, `~/Library/Application Support`), the Documents directory on iOS); every platform uses the bundled SQLite driver and `Dispatchers.IO`. Tests use an in-memory database (`inMemoryRecipeDatabase()` in `commonTest`) and must never build the real one. A schema change needs a new database `version`, a migration and the exported schema in `schemas/`.
  - `:feature:recipe:ui`: Compose Multiplatform screens (Android, jvm, iOS), depends on `domain` (`implementation`: consumers never need domain types from it). Its only public declarations are the navigation key `RandomRecipeNavKey`, the entry registration `EntryProviderScope<NavKey>.randomRecipeEntry()` (both in `RandomRecipeNavKey.kt`, called from `:composeApp`'s navigation) and the Koin module `recipeUiModule`; everything else is `internal`. `randomRecipeEntry()` maps `RandomRecipeNavKey` to `RandomRecipeRoute`, which gets `RandomRecipeViewModel` via `koinViewModel()`, collects its `RandomRecipeUiState` `StateFlow`, and passes state and callbacks to the stateless `RandomRecipeScreen`. Follow this NavKey + entry registration (public) / Route (stateful) / Screen (stateless) layering and keep visibility as tight as possible in new features. Images load with Coil 3 (`coil-network-ktor3`). Consumed by `:composeApp`; it does not build an iOS framework itself.
  - `domain` and `data` are KMP rather than `kotlin("jvm")` so iOS can consume them. Their Android consumers resolve the `jvm()` variant, except for modules with an `android` target (`meals.kmp.room`).
- `feature/about/` has only a `ui` module, `:feature:about:ui` (no domain or data yet). Its tab has five screens, registered by `aboutEntries(onNavigate, onBack, content)` (`AboutNavigation.kt`): `AboutScreen` (`AboutNavKey`, the tab root) with "License", "Libraries", "Privacy" and "Attributions" buttons, which call `onNavigate` with `LicenseNavKey`, `LibrariesNavKey`, `PrivacyNavKey` or `AttributionsNavKey`; `:composeApp` passes `navigator::navigate`, which pushes the key onto the about tab's back stack. (One `onNavigate` instead of a callback per button keeps `aboutEntries` within detekt's parameter limit.) `content` is an `AboutContent` with the loaders for the license, privacy policy, attributions and library JSON, which only `:composeApp` can provide. All sub-screens have the design system's `BackTopAppBar` (title + back button; desktop has no system back).
  - License, Privacy and Attributions share `TextDocumentRoute`/`TextDocumentScreen` (title + loader). `toTextBlocks()` (`TextBlock.kt`) splits the text into blocks: `#` lines become headings (`PRIVACY.md` and `ATTRIBUTIONS.md` are Markdown; nothing else of Markdown is supported), and each paragraph's lines are joined so the text wraps to the screen instead of keeping the file's line breaks.
  - Libraries: `LibrariesRoute` loads the app's libraries and licenses with `produceLibraries`, `LibrariesScreen` shows them with AboutLibraries' `LibrariesContainer` (`aboutlibraries-compose-m3`).
  - It has no ViewModel and no Koin module. A feature only needs the layers it uses. Features never navigate themselves: they take callbacks, and `AppNavigation` maps them to `Navigator` calls.
- The about screens' content comes from `:composeApp`, not the about module, as Compose resources generated on every build. `generateAppComposeResources` (a `Sync` task) assembles `build/generated/appComposeResources/files/` from `aboutlibraries.json` (the AboutLibraries Gradle plugin's `exportLibraryDefinitions`: only `:composeApp` sees every dependency; it fetches license texts from SPDX, so it needs network unless cached) and the repository root's `LICENSE`, `PRIVACY.md` and `ATTRIBUTIONS.md`, so the app shows the same texts as the repo. The task's output, `build/generated/appComposeResources/`, is `:composeApp`'s commonMain Compose resources directory (`compose.resources { customDirectory(...) }`); it also copies in `src/commonMain/composeResources` (the module's strings), which would otherwise be ignored. Add other generated files to the `Sync` task. `AppNavigation`'s `aboutContent` loads the files with `Res.readBytes("files/...")`. `filterVariants` limits library collection to what ships (`android`, `jvm`, `metadataIosMain`). `androidResources.enable = true` in `:composeApp` (and, through `meals.kmp.compose`, in every Compose library module) is required for Compose resources to reach the Android app. The plugin also adds an empty `res/raw/aboutlibraries.json` through its own Android hook; it is unused.
- `core/` holds code shared by all features (KMP; jvm + iOS, and no Android or Compose dependencies except in `:core:designsystem`):
  - `:core:designsystem`: the app's theme, `MealsTheme`, applied once in `App()`, and components shared by features in its `component` package (`BackTopAppBar`: title + back button for screens below a tab's root). These are its only public declarations; its strings ("Back") are in its own Compose resources (`packageOfResClass = "io.github.fmweigl.yetanothermealsapp.core.designsystem.resources"`). A food palette as full Material 3 light and dark color schemes (`Color.kt`: paprika primary, basil secondary, saffron tertiary, cream surfaces in light mode, espresso in dark), serif display/headline/titleLarge styles (`Type.kt`, the platform serif; no bundled font) and rounded shapes (`Shape.kt`). Follows the system dark mode. Screens use `MaterialTheme.colorScheme`/`typography`/`shapes` roles, never hard-coded colors, corner radii or font families. `ColorContrastTest` checks every on-color pair for WCAG AA (4.5:1); keep it passing when changing colors. Android's window theme (`androidApp/src/main/res/values{,-night}/themes.xml`, `Theme.Meals`) only sets the window background to the schemes' `background` so launch doesn't flash; keep the two in sync.
  - `:core:domain`: the typed `Result<D, E : Error>` (with `map`/`flatMap`/`onSuccess`/`onFailure`), the `Error` marker interface, and `DataError` (`NoConnection`, `Timeout`, `Server`, `InvalidResponse`, `NotFound`, `Storage`, `Unknown`). Feature `domain` modules expose it with `api(projects.core.domain)`.
  - `:core:network`: the app's single TheMealDB `HttpClient`: base URL (V2 API, `https://www.themealdb.com/api/json/v2/{key}/`, with the generated `THE_MEAL_DB_API_KEY`), `expectSuccess = true`, JSON content negotiation, and the platform engines (OkHttp on `jvm`, Darwin on iOS). Its Koin module `coreNetworkModule` provides the client; features inject it and never create their own. The public `createTheMealDbHttpClient(engine, apiKey = "1")` exists for tests with a `MockEngine`; it defaults to the test key so request URLs in tests don't depend on the configured key.
  - `:core:data`: `safeApiCall { }`, which runs a Ktor request and maps its exceptions to `DataError` (rethrowing `CancellationException`). Relies on `expectSuccess = true`.
- Error handling: repositories return `Result<T, DataError>` and never throw; Ktor and serialization exceptions stay inside `data`. Wrap every request in `safeApiCall` and return `DataError.InvalidResponse` for responses that parse but can't be mapped (mappers return null rather than throwing), `DataError.NotFound` when a lookup has no result. Database operations are wrapped in `safeDbCall`, which maps `SQLiteException` to `DataError.Storage`; flows from the database catch it themselves (a `Result` in the flow, or a safe default such as `false`). ViewModels put the `DataError` into their UI state, and `ui` turns it into a message (`DataError.toMessage()`, a `StringResource`).
- User-facing strings live in Compose resources (`src/commonMain/composeResources/values/strings.xml`), never as literals in code, in the module that shows them: each feature `ui` module, `:core:designsystem` (shared components), `:composeApp` (tab labels) and `:desktopApp` (window title, `src/main/composeResources`). Read them with `stringResource(Res.string.x)` in composables; non-composable code returns a `StringResource` (e.g. `DataError.toMessage()`, `TopLevelDestination.label`) and the composable resolves it. Each feature `ui` module sets `compose.resources { packageOfResClass = "io.github.fmweigl.yetanothermealsapp.<feature>.ui.resources" }`, because the default package comes from the project name (`ui`), which would clash. The Android app name stays in `androidApp`'s `res/values/strings.xml`; the documents (license, privacy policy, attributions) come from the repository root files.
- Accessibility (screen readers): images described by nearby text are decorative (`contentDescription = null`); titles and section headings get `Modifier.semantics { heading() }`; rows that belong together (an ingredient and its measure) are one element (`semantics(mergeDescendants = true) {}`); progress indicators get a "Loading" `contentDescription`; content that appears while focus stays elsewhere (a new recipe after "Next", an error) gets a `paneTitle`, which Android announces when it appears (a `liveRegion` would only announce changes to an existing node). `RandomRecipeScreenAccessibilityTest` checks this for the recipe screen.
- Platform-specific code goes in `expect`/`actual` declarations.
- Dependency injection uses Koin (`koin-core`, `koin-compose`, `koin-compose-viewmodel`). Each feature layer exposes its own Koin module in a `di` package (e.g. `recipeDataModule` binds the repository, `recipeUiModule` declares ViewModels with `viewModelOf`). `:composeApp`'s `initKoin()` registers them, together with `coreNetworkModule`, via `startKoin`; Koin is not started inside Compose. Screens obtain ViewModels with `koinViewModel()`, which uses the globally started Koin. Add new feature modules to the list in `initKoin()`.
- Lifecycle ViewModel and runtime-compose (JetBrains multiplatform artifacts) are available in every feature `ui` module's `commonMain` through `meals.kmp.feature.ui`.
- Dependencies and versions are managed in `gradle/libs.versions.toml`, which uses bleeding-edge versions (AGP 9.x, Kotlin 2.4.x, compileSdk 37). JVM target is 11. Package/namespace: `io.github.fmweigl.yetanothermealsapp`.

## App icon

A two-pronged fork shaped like a "Y" with a saffron leaf, cream on a basil-green disc and background (MealsTheme colors). The source is `art/app-icon/render_icons.py`, which holds the motif as SVG on Android's 108×108 adaptive-icon grid and renders, with Inkscape and Pillow (`python3 art/app-icon/render_icons.py`):
- Android's legacy launcher PNGs (`mipmap-*dpi`, only used on API 24–25),
- iOS's 1024 px light, dark and tinted icons (`iosApp/iosApp/Assets.xcassets/AppIcon.appiconset`, opaque RGB),
- the desktop icon: `desktopApp/src/main/resources/icon.png` (the window icon, set in `main.kt`, and the Linux package icon) plus `desktopApp/icons/icon.ico` and `icon.icns` for the Windows and macOS installers.

Android 8+ uses the adaptive vector icon (`drawable/ic_launcher_background.xml`, `ic_launcher_foreground.xml` and `ic_launcher_monochrome.xml` for themed icons), which is hand-written: change it together with the script's `MOTIF` and re-run the script.

## Store listing

The Google Play listing lives in `fastlane/metadata/android/en-US/` (Fastlane's layout, which F-Droid also reads): `title.txt` (≤ 30 characters), `short_description.txt` (≤ 80), `full_description.txt` (≤ 4000) and `images/` with `icon.png` (512×512), `featureGraphic.png` (1024×500) `phoneScreenshots/1.png`… (1080×1920, Play's maximum aspect ratio is 2:1), `sevenInchScreenshots/1.png` (1080×1920) and `tenInchScreenshots/1.png` (1440×2560). All PNGs are opaque RGB. Nothing uploads it yet; it's entered in Play Console by hand. Keep the descriptions true to what the app does, and update them (and the screenshots) when features or screens change. The listing is written around the app's only feature, random recipes: when adding a feature (search, favorites, categories, ...), revisit the feature graphic's tagline ("A random recipe, one tap away", `TAGLINE` in `render_store_graphics.py`, then re-render), `short_description.txt` ("Random recipe ideas from around the world...") and `full_description.txt`, and tell the user about it.

- `art/play-store/render_store_graphics.py` renders the icon (the launcher icon's motif from `render_icons.py`) and the feature graphic. Its text uses Noto Serif from `art/fonts/` (OFL, `art/fonts/OFL.txt`; only used for artwork, not shipped), the serif the app's headlines use on Android.
- Screenshots never show TheMealDB's photos: they come from contributors, none is marked Creative Commons, and many seem to come from the recipes' source sites, so their use in a store listing is unclear. They show the debug build's **screenshot mode** instead: two recipes written for the screenshots (`androidApp/src/debug/.../ScreenshotRecipes.kt`) with illustrations drawn by `art/play-store/render_mock_recipes.py` (`art/play-store/mock-recipes/`). `debugModules()` (`src/debug/.../DebugModules.kt`; the `src/release` version returns nothing) replaces the `RecipeRepository` when the app's files contain a `screenshot-mode` directory with the images. `initKoin()` runs the platform `config` after loading the app's modules, so that override wins. Set it up with `adb shell run-as io.github.fmweigl.yetanothermealsapp mkdir -p files/screenshot-mode` and `adb exec-in run-as io.github.fmweigl.yetanothermealsapp sh -c 'cat > files/screenshot-mode/<name>.png' < art/play-store/mock-recipes/<name>.png`, and remove the directory afterwards.
- Screenshots come from the Android emulator via `adb exec-out screencap` (never from the desktop): `adb shell wm size 1080x1920` for Play's aspect ratio, System UI demo mode for a clean status bar (12:00, full battery, no notification icons), `cmd uimode night yes|no` for light and dark. The current set: 1 shakshuka (light), 2 its ingredients (light), 3 spaghetti (dark), 4 privacy policy (dark). Tablet screenshots come from the same phone emulator, resized: 7-inch `wm size 1080x1920` + `wm density 280`, 10-inch `wm size 1440x2560` + `wm density 320`, both portrait (the recipe screen has no landscape/tablet layout yet, so landscape shows only the photo); the current set is shakshuka (light) for each. Each `wm size` change can make demo mode stack duplicate Wi-Fi/signal icons that only a SystemUI restart clears (no root on this image): check the status bar and, if needed, fix it in the PNG. Restore the emulator's size, density, theme and demo mode afterwards.

## Data source

Recipes come from TheMealDB JSON API, version 2 (supporter/premium). The supporter key is a secret of the maintainer: never commit it, print it or put it in docs or test fixtures; it lives in the maintainer's `local.properties` (see `theMealDbApiKeySource()` above). Being in the request URL, it does end up in the shipped app; that's accepted. The API reference is in `docs/themealdb-api.md`, and the project skill `.claude/skills/themealdb` covers using it.
